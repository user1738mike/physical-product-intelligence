# System architecture

## Modular monolith
Next.js renders the public foundation page and account/organization context screen. Django/DRF owns the API and application services; PostgreSQL is the authoritative database. Deploy frontend and API behind one TLS ingress using /api/v1 routing to avoid broad CORS. Compose is local development infrastructure, not a production deployment recipe. No microservices or Kubernetes are required.

Implemented backend modules: operations, accounts (existing Django user/session identity), organizations (tenants, memberships, role services), audit (security and administrative history) and products (catalog identity/revisions, live packaging configurations/history, typed claims, verification/selection and evidence metadata). Ingestion adds private bounded imports and review; compatibility adds equipment, immutable rules and deterministic assessment snapshots. External integrations remain deferred. Business writes and successful audit events share database transactions. Next.js provides organization selection, searchable/paginated catalogs, create/detail/edit forms, packaging lifecycle controls, evidence/verification/conflict review and scoped history through the existing same-origin session transport.

## API and isolation
Customer endpoints live under /api/v1/ and use DRF with an OpenAPI contract. Health/schema expose no customer data. DRF denies access by default; only health, schema, CSRF-token retrieval, registration and login are public. Sessions use Django's database storage, HttpOnly/SameSite=Lax cookies, eight-hour expiry and production Secure/TLS. Explicit CSRF wrappers protect anonymous login/registration as well as DRF's authenticated-session CSRF checks. Next.js uses a server-only API route with a fixed backend origin, explicit header/cookie forwarding, bounded request bodies, a timeout and no automatic request replay; production should route API requests directly at the shared TLS ingress. No browser token storage or permissive CORS is installed.

Phase 2 resolves current organization membership on every request, enforces role permissions in services, and scopes every nested membership/audit query by the authorized organization. Organization identifiers supplied by callers are never authority. Writes lock the organization, then recheck membership; ownership transfer is serialized with revocation and role changes. Database constraints enforce membership uniqueness, valid roles and at most one owner. Supported services preserve the last owner. Slugs/ownership fields cannot be reassigned through generic payloads. Inaccessible resources return 404, role denials 403. Staff grants no tenant API bypass. PostgreSQL RLS remains deferred; isolation is application-enforced and tested. See ADR 0006 for the policy and migration-safe identity decision.

## Storage and jobs
Product ownership is stored once on Product.organization; dependent records follow protected foreign keys. Every nested lookup starts from the authorized organization and product. Writes lock the organization to serialize with membership changes and then lock the product/profile; product PATCH and packaging edits use optimistic versions to reject stale submissions. Product revisions and configuration revisions preserve history. Owner/admin controls lifecycle, physical verification and canonical claim selection; members contribute reported/estimated observations and read scoped history. PostgreSQL deferred constraint triggers validate same-product provenance, ordered snapshot containment, claim/profile scope and verification consistency at transaction commit. They are not RLS or DB-level immutability; read-only admin/ORM guards remain supplemental. See ADRs 0007/0008.

The evidence module will own a private S3-compatible storage adapter, opaque object keys, encryption, checksums, upload limits and short-lived authorized download grants. No media URL or public bucket is configured now. Quarantine and malware inspection precede evidence availability. Introduce Celery/Redis when ingestion or assessment workflows need durable background work; use idempotency keys, retry limits and transaction-on-commit dispatch. An outbox may be required before externally delivered events.

Current Evidence records are reference-only provenance metadata in the products module. No URL is fetched, file bytes accepted, private object key supplied or digest verified. An optional declared SHA-256 remains explicitly unverified. Artifact capture, licensing verification and retention-aware deletion must be designed before file ingestion.

## Observability and configuration
JSON request logs contain request identifiers, method, path without query strings, status and duration; they exclude request bodies, headers and secrets. Client-supplied request IDs are validated. Liveness checks the process; readiness executes SELECT 1 and returns a generic failure. Metrics are an internal authenticated/scraped ingress concern: derive request counts, latency and error rate from logs initially; dedicated exporters and error-reporting providers are integration points, not installed integrations. Health traffic must be rate limited at ingress.

Development permits HTTP on loopback. Testing uses PostgreSQL in CI/Compose, with opt-in SQLite unit smoke tests only. Production requires secrets, explicit hosts and trusted HTTPS CSRF origins, enforces secure cookies/HSTS/TLS redirect and never enables debug. TLS proxy header trust is opt-in and requires ingress to strip forged client headers.

## Phase 4 ingestion increment

The ingestion module now owns private upload/job metadata, source rows, per-attribute candidates and immutable review records. It reuses product Evidence/revisions/claims and current tenant authorization. Bounded subprocess adapters parse CSV, XLSX and narrowly labeled PDF/TXT. Synchronous application locks the organization, checks target versions/evidence snapshots, and commits catalog/source/history/audit results atomically. No queue, OCR, model provider, public media route or compatibility service was added. See [ADR 0009](architecture-decisions/0009-bounded-reviewable-ingestion.md) and [ingestion operating guide](ingestion-api.md) for storage/scanner/worker requirements. Earlier future-storage statements describe the pre-ingestion foundation; this increment implements the bounded private local path, with object storage and durable quarantine/workers still deployment work.

## Phase 5 compatibility increment

The compatibility module implements Equipment/EquipmentRevision, immutable RuleSet/RuleActivation and immutable Assessment. A pure Decimal engine consumes captured catalog claims and explicit scope/orientation; transaction services reuse organization locks, current membership and audit. Reference guards supplement service checks. The Next.js equipment and assessment workspaces use existing session/CSRF transport. No new runtime dependency or background infrastructure is introduced. Earlier constraints/assessment deferrals above describe historical milestones and are superseded by this increment. See [ADR 0010](architecture-decisions/0010-versioned-equipment-and-deterministic-assessments.md) and the [operating guide](compatibility-api.md).

## Phase 6 AI assistance

Optional AI extraction runs through existing ingestion jobs, candidate review and transactional apply. The provider protocol has one optional OpenAI SDK adapter, disabled by default and independent of core startup. Synchronous bounded leases avoid database locks during external work; explicit retry/cancel/recovery controls replace an unneeded queue. Source and response schemas are validated by application code. AI has no tools or rule/assessment write path; Phase 5 remains authoritative. See [AI guide](ai-extraction-api.md) and ADR 0011.
