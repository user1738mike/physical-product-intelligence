# Testing strategy

Phase 1 checks process liveness, successful database readiness, generic readiness failure, safe request IDs, production missing/unsafe configuration, security checks and OpenAPI validation. Backend tests use Django's runner. PostgreSQL is required in Compose and CI; explicitly selected SQLite is a local smoke option and cannot prove PostgreSQL compatibility. Frontend tests inspect the rendered landing component and health response semantics using Vitest, followed by TypeScript, ESLint, Prettier and the Next.js production build.

CI runs on pull requests and pushes with PostgreSQL, backend formatting/linting/tests/schema validation, frontend install-from-lock/checks/tests/build and a Compose smoke job. Compose smoke verifies actual API/database readiness, frontend readiness and migrations. Logs from failed containers assist diagnosis without publishing environment files. CI is configured but only an actual CI run proves runner behavior.

Phase 2 tests cover anonymous denial, explicit CSRF checks for login/registration/tenant writes, generic failed/inactive login, logout replay denial, session/password/deactivation expiry, authentication throttles, privileged-field rejection, caller-only initial ownership, retries/uniqueness/role constraints, two-tenant lists/detail/create/update/delete/nested/transfer denials, crafted organization reassignment, staff bypass denial, suspension/reactivation, last-owner policy, audit immutability/metadata/rollback and concurrent PostgreSQL transfers. Tests assert stored state and audit outcomes as well as status. The frontend suite verifies fresh CSRF after login, cookie policy, failed CSRF preventing credential submission, external URL rejection and accessible loading output. `scripts/phase2_smoke.py --allow-create-test-data` exercises actual Next-to-Django registration/session/tenant/audit/logout flows only against a disposable database. Invitation delivery is deferred, not tested as implemented.

Later gates add unit/dimension conversions, threshold/uncertainty boundaries, deterministic replay, evidence authorization, malformed uploads and retry idempotency. PostgreSQL constraint/transaction tests are mandatory; SQLite skips the concurrent row-lock test. Production ingress/TLS/cookie behavior and full interactive keyboard/accessibility validation remain staging/release checks.

Release gates include migration review, dependency advisory review, production configuration check, restore drill and a staging smoke test. Test results must distinguish executed/passed, failed and unavailable checks. No coverage percentage alone is evidence of isolation or correctness.

Phase 2 acceptance follow-up adds legacy Django username login coverage, registration-only browser validation, membership selection beyond 25 organizations, duplicate-free page merging and refreshed server roles. Live smoke repeats authenticated CSRF/profile reads to catch proxy socket resets. Browser automation remains a separate check when a browser is connected; API smoke and rendered-form tests do not claim a completed interactive keyboard/accessibility review.

The final security pass also verifies that login rotates the CSRF secret, rejects a pre-login token, and issues Secure session/CSRF cookies under HTTPS settings. Live smoke defaults to 50 CSRF/profile pairs per account (200 reads total); `--read-cycles` changes that count. It verifies non-cacheable responses, missing-token and hostile-origin denial, cookie attributes, ordinary-member denial, permitted admin writes, owner-only denial, removal revocation and logged-out session replay denial. Its client obtains CSRF for bodyless DELETE as well as JSON mutations. Use only a disposable database; the script intentionally retains fixture accounts and organizations.

Phase 3 adds the `products` test module to every full backend test command and CI. Tests assert tenant-unique SKUs, initial snapshot atomicity, complete numbered revisions, metric normalization down to 0.000000001 kg, uncertainty bounds, retained competing observations, explicit unknowns, invalid dimensions/nonfinite/overprecision values, packaging cycles/counts/levels, immutable history, denied nested identifiers across products/revisions, source secrecy in audit, actor deletion retention, archived history, member/admin permissions, revocation/suspension/staff denial, pagination, CSRF and audit-failure rollback. PostgreSQL concurrent writers must both persist with distinct sequential revision numbers; SQLite cannot verify that lock behavior.

`python scripts/phase3_smoke.py --allow-create-test-data` exercises product/evidence/packaging APIs through the production Next.js proxy using actual login/session/CSRF, tenant denial, exact normalized values, provenance links, historical edit denial, member contributions, owner-only archival, reactivation, revocation and logout. It creates/retains fixture data and must only target a disposable database. CI runs it after Phase 2 smoke. No upload/quarantine/checksum-verification, assessment, product UI or production ingress behavior is claimed as tested.

The completion increment extends that smoke with searchable catalog PATCH/stale denial, live packaging versions/lifecycle, reported/estimated claims, unauthorized verification/selection denial, documented physical attestation, conflict resolution, retained estimates and member-scoped history. `test_workflows.py` adds API/ORM/PostgreSQL checks, including simultaneous stale edits and deferred structural provenance guards. Frontend tests cover typed versioned requests, encoded search, structured API errors, explicit units, source fields, role-dependent controls and distinct unknown/conflict/estimated/attested states. Real browser verification is recorded separately in the completion report; the earlier UI deferral above refers to the initial API-only pass. CI discovers all backend tests through the products app and runs the expanded smoke without adding extra registration fixtures that exceed the Phase 2 signup throttle.

## Phase 4 ingestion increment

The ingestion PostgreSQL suite exercises authenticated multipart/CSRF, tenant-scoped jobs/downloads/reviews/reports, MIME/size/path and malformed document handling, CSV BOM/quoting/header/row limits, XLSX formulas/archive limits, deterministic PDF/text extraction, equivalent/conflicting claims, stale targets, rollback and concurrent idempotent apply. Frontend tests cover multipart CSRF, the isolated larger upload-body allowance, binary attachment forwarding and versioned review transport. The existing Phase 3 smoke reuses its two users to invoke Phase 4 integration coverage, avoiding an additional signup-throttle batch. Use `python manage.py test accounts organizations operations products ingestion` and the commands in the completion report.

## Phase 5 acceptance increment

Full PostgreSQL command: `python manage.py test accounts organizations operations products ingestion compatibility --settings=config.settings.test`. Tests cover profile lifecycle, immutable rule/specification/snapshot history, all supported rule types, exact/inside/outside boundaries, Decimal conversions/margins, intervals, explicit orientation/level, missing envelope maxima, estimates/measured policy/conflicts, stable retries/parents/comparison, stale and concurrent writes, rollback/audit, PostgreSQL structural guards, bounded claims, history query count and authenticated CSRF/role/tenant denial. Frontend tests verify transport, errors, provenance distinctions, escaping and readable retained limits. The existing Phase 3 smoke invokes Phase 4 and Phase 5 using the same two disposable users. Actual native and browser results, with Docker/CI limitations, are in the [completion report](phase5-completion-report.md). Tests do not certify physical hardware behavior.

## Phase 6 mocked provider verification

The existing ingestion app discovers test_ai.py in the full PostgreSQL suite. It tests strict JSON/types/units/citations, unknown/quarantined values, parser bounds, prompt-injection fixtures, deterministic normalization/equivalence/conflicts, source privacy, explicit corrections/selections, stale/repeated/concurrent approval/application, rollback, processing leases/retry/cancellation and immutable assessment integration. Optional SDK tests use mocked clients and in-memory HTTP transport; no live key or request is required. CI installs requirements-ai.lock in the native backend job and explicitly disables AI; core-only Compose skips only the three optional SDK tests. The disposable Phase 3 proxy smoke now includes disabled-provider Phase 6 checks that create no extraction job or provider call. Browser fixtures are clearly labeled offline mocks. See [actual results](phase6-completion-report.md).
