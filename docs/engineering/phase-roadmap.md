# Phase roadmap

Phase 9B adds provider-independent internal statements/prices, durable operations, a verified-event inbox, settlement/refund allocations, linked corrections, fenced recovery and owner/admin billing history. Only an isolated offline simulator is executable; no real gateway, merchant, customer prices, tax policy or live collection is selected. See [billing API](../billing-api.md), [operations](../billing-operations.md) and [actual results](../phase9b-completion-report.md). Phase 9A's verified local boundary is preserved separately. Hosted CI, fresh Grype acceptance and approved staging remain release gates.

Phase 9A adds the manual commercial foundation: immutable plan versions, non-overlapping access assignments, centralized entitlement/capacity checks, UTC monthly assessment/extraction reservations and append-only usage, operator commands and owner/admin Plan and usage UI. See [API](../commercial-api.md), [operations](../commercial-operations.md) and [actual verification](../phase9a-completion-report.md). Earlier statements that these features are absent are historical. Payment integration remains future work. Phase 8 scan, exact-candidate hosted CI and approved staging gates remain open; no deployment is implied.

Phase 8 current status: production-like local HTTPS deployment rehearsal and release tooling implemented; see the [capability/deployment matrix](../phase8-deployment-plan.md), [checklist](../phase8-release-checklist.md) and [actual final verification/readiness report](../phase8-completion-report.md). Real scanner fail-closed behavior, isolated database/private-file recovery and prior-code compatibility are locally exercised. Historical Phase 1–7 blockers below are superseded only where the new report provides evidence. No remote staging/production deployment or live AI request occurred. Hosted CI for the exact committed candidate, artifact vulnerability acceptance, real infrastructure, monitoring/retention and explicit pilot commercial process remain release gates. Subscriptions, entitlements, commercial usage metering and billing remain absent; paid public launch is not approved.

Phase 1: foundation implemented; its normal Docker startup verification remains open because host address pools were exhausted. Preserve volumes and other projects' networks when resolving that blocker.

Phase 2: identity, session/CSRF authentication, organizations, owner/admin/member services, membership-derived tenant boundaries, audit history, reviewable migrations and account/organization frontend implemented. Native PostgreSQL tests and frontend checks are recorded in [the execution report](../phase2-implementation-report.md). Acceptance requires the report's final checks and explicit review of remaining runtime/deployment limitations.

Deferred within identity operations: email verification/invitations, recovery, MFA/SSO, distributed abuse controls, privileged audit archival/purge and immutable retention sink. These are launch decisions, not implemented features. Operator provisioning is explicit through Django's trusted admin mechanisms. Production requires a verified shared TLS ingress, origin/header policy and backups.

Phase 3: structured product identities with tenant-unique SKUs, immutable numbered revisions, packaging hierarchy snapshots, exact metric observations/uncertainty, reference-only evidence provenance and tenant-scoped APIs are implemented. See [API guide](../product-api.md), ADR 0007 and [execution report](../phase3-implementation-report.md). All existing roles may contribute product data; owner/admin controls archival. New evidence and revisions cannot change prior snapshots. Membership revocation, tenant suspension, cross-product provenance denial and concurrent revision allocation are tested.

Phase 3 completion adds the usable catalog/search/pagination/create/detail/edit screens, independently named packaging profiles with optimistic versions and immutable descriptor history, typed attribute claims, owner/admin physical-measurement attestations, explicit claim selection/rationales and member-readable scoped history. Reported, estimated, verified, unknown and conflicting values are distinct. PostgreSQL provenance guards backstop same-resource references. See ADR 0008 and the [completion report](../phase3-completion-report.md) for actual checks, browser verification and remaining environment gates.

Phase 4: private bounded CSV/XLSX import, labeled PDF/TXT extraction, candidate review/correction, reported provenance, explicit canonical selection and atomic retry-safe application are implemented. See [ingestion guide](../ingestion-api.md), ADR 0009 and the [completion report](../phase4-completion-report.md). Malware scanning integration, object storage, durable isolated workers and retention remain deployment requirements. Compatibility/assessment/rule execution, OCR/AI vision, billing and Phase 5 are not implemented. Production TLS/ingress, abuse limits, retention/deletion and any unexecuted Docker/hosted CI checks remain release gates.

Phase 5: equipment specification histories, immutable typed rule sets and activation, deterministic Decimal compatibility, frozen evidence/results and tenant-scoped API/UI workflows are implemented. See [guide](../compatibility-api.md), ADR 0010 and [completion report](../phase5-completion-report.md). This supersedes the Phase 4 paragraph’s historical Phase 5 deferral. Native PostgreSQL and browser/proxy checks passed; Docker networking and hosted CI remain separate release gates. Phase 6 has not started. Agree its actual requirements and resolve production ingress, storage/scanner, shared abuse protection, retention/restore and hardware-validation responsibilities before release.

Phase 6: optional AI-assisted source-grounded extraction into existing import/review workflows is implemented. Deterministic validation, explicit human approval/selection, source privacy and frozen assessment provenance remain authoritative. See [guide](../ai-extraction-api.md), ADR 0011 and [completion report](../phase6-completion-report.md). Live provider quality/access remains unverified by user instruction. No Phase 7 work is included; agree its scope and resolve production privacy, ingress, worker limits, storage/scanning and release verification first.

Phase 7 adds shared PostgreSQL limits/global extraction admission, bounded production server recipes, safe project Docker network recovery, production TLS/role/private dependency policy, scanner hook, redacted operational diagnostics and isolated backup/restore/restart verification. CI and a separate opt-in provider command plus versioned synthetic validation suite are implemented. See [ADR 0012](../architecture-decisions/0012-small-deployment-operational-controls.md), the [operations/release checklist](../deployment-and-operations.md) and [actual evidence and blockers](../phase7-completion-report.md). Prior phase deferrals are historical. Next work should resolve hosted CI and controlled staging gates, including real ingress/roles/scanner/storage/recovery/load validation. No Phase 8 feature, deployment, commit/push or live provider call is included.
