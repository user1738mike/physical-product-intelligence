# ADR 0009: Bounded, reviewable evidence ingestion

Status: implemented, 2026-10-15. Extends ADR 0008 without replacing its provenance or authorization policy.

The ingestion Django module owns private upload metadata, import jobs, source rows, per-attribute candidates and append-only review records. It does not introduce a second product Evidence model. Applied rows create ordinary product Evidence and link exact source bytes through the row/job relationship. Source checksums are computed server-side and rechecked on reads. A digest proves byte identity, not supplier authenticity, licensing or physical accuracy.

Use Django's `ingestion` storage alias. Local storage is outside frontend/static paths, with opaque organization/UUID keys, restrictive local permissions and no public URL. Only authenticated, freshly authorized organization members can download via the API. Downloads are attachments with nosniff and sandbox headers. Production uploads fail closed without a configured scanner; local development/test explicitly permit visibly unscanned fixtures. Scanner implementations must be bounded, fail closed, and deployed with their own operational monitoring.

There was no durable background-task infrastructure. This increment deliberately uses synchronous, bounded subprocess parsing. The subprocess receives bytes and parser options, never Django credentials; it has no database interface, tool calls, model prompts or executable source evaluation. CSV, XLSX and labeled text-based PDF/TXT adapters return the same bounded rows. Linux applies address-space/CPU limits; every platform applies a wall timeout and input/output limits. Windows does not provide the Linux hard memory limit. Production processing requires restricted worker containers/process identities, no egress, scanner integration, bounded concurrency and durable retries before increasing limits or accepting hostile Internet-scale workloads. This process is not a complete OS sandbox.

Lifecycle: uploaded → validating → uploaded (preview) or failed; uploaded with explicit mapping → processing → awaiting_review; reviewed jobs → completed/completed_with_errors; eligible jobs → cancelled. Validating/processing occur inside a synchronous transaction, so concurrent readers usually see the preceding stable state. Candidate decisions carry approval rather than a separate job-level approved status. Clients never set lifecycle/ownership/source keys directly. Failed validation may be retried; completed/cancelled jobs cannot be edited or reprocessed. Applying a completed job returns its existing result.

All current members upload, validate, map and inspect candidates. Owner/admin alone approves/rejects/corrects, grants new-product creation, cancels, refreshes comparisons or applies catalog changes. This matches existing lifecycle/selection authority. No import path creates measured claims or ClaimVerification. Numeric acceptance creates reported claims, with explicit optional canonical selection and rationale. Existing measured evidence remains immutable. Text/packaging descriptor changes require explicit approval; contradictory approved descriptor values or canonical selections abort the entire apply instead of choosing a last row. All approved numeric claims are recorded before selections are made.

Row snapshots identify SKU within the authorized organization, expected product revision, packaging identity/version and existing claim IDs/values. Organization locks serialize application with membership changes and catalog writes. Stale targets/comparisons return 409; refresh invalidates decisions and preserves review history. The entire application is one transaction including domain writes, source links, candidate result links, job results and audit success events. A failure rolls everything back. Partial success is limited to explicitly rejected candidates/invalid rows, and completion counters report that choice. No database or volume reset is needed.

Duplicate checksums produce warnings only; they do not merge business records. Identical mapped rows within a job remain visible as duplicate rows requiring rejection. Equivalent metric values are compared using exact Decimal normalization. Different measurements retain separate claims; no averaging or last-write-wins rule exists. Separate explicitly reviewed jobs may record another source assertion of the same value. Retrying one job never duplicates its output. Mappings are job-specific; reusable tenant presets are deferred rather than implementing unsafe global reuse.

Document extraction is intentionally narrow: one labeled product per page, explicit SKU and units, supported labels only. Scans, arbitrary tables/layouts, OCR, DOC/DOCX, XLS/XLSM, AI extraction and URL fetching are unsupported. Formula cells are marked unsupported, never evaluated, including cached values. XML parsing uses defusedxml; ZIP expansion, relationships, active content and entry counts are bounded/restricted. PDF parsing uses pinned pypdf under the subprocess limits. See the [openpyxl security documentation](https://openpyxl.readthedocs.io/en/stable/) and [pypdf text extraction limits](https://pypdf.readthedocs.io/en/stable/user/extract-text.html).

Uploaded bytes, previews, raw cells, normalized candidates, corrections and rejection decisions contain customer data. Only fixed actions and IDs enter the existing AuditEvent metadata. Ordinary APIs do not edit/delete uploads, review history or source evidence. Trusted database/storage operators remain privileged; no new RLS or cryptographic history immutability is claimed. Quotas bound retained storage but lifecycle-aware retention, legal hold, orphan reconciliation, encrypted object storage, backups and tenant-specific deletion remain deployment work. No compatibility engine, AI vision or Phase 5 is included.
