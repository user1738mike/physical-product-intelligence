# ADR 0006: Phase 2 identity, sessions, ownership and audit

Status: accepted. Existing Phase 1 uses `auth.User`; framework migrations were already applied during native PostgreSQL verification. Retain this model and its foreign-key identity. Do not change `AUTH_USER_MODEL`, rewrite migrations or reset databases. Identity is a unique, case-sensitive Django username, not email; registration permits ASCII letters, digits, dot, underscore and hyphen. Email identity/verification, invitations, password recovery, MFA and SSO are deferred. Public registration creates only an ordinary active user, with Django password validation/hashing. Operators use `createsuperuser` for trusted admin provisioning.

Use database-backed Django sessions, HttpOnly session cookies, SameSite=Lax, an eight-hour absolute expiry, browser-close expiry and Secure cookies in production. Login rotates the session and CSRF token; logout flushes it. Password changes and inactive accounts invalidate authentication through Django's existing backend. Unsafe requests require CSRF, including anonymous registration and login: DRF's authenticated-session CSRF behavior alone is insufficient for login. `/api/v1/auth/csrf/` returns the masked token in a non-cacheable response. The browser stores no authentication tokens. Production routes API and frontend through one TLS origin; no CORS policy is added. Next.js proxies `/api/v1/` locally to the backend, preserving the browser Origin and letting Django check an explicit trusted development origin. Proxy destinations are server-only, fixed at build time; no public credentials are configured.

Organizations have UUID identities, unique immutable slugs, names and an active flag. Organization creation and owner membership are one transaction. A repeated slug conflicts cleanly with no partial membership. Owners/admins/members may view the organization and member list. Owners/admins may update its name and add/remove ordinary members. Only owners may assign/change admin roles, remove admins, suspend/reactivate the organization or transfer ownership. Admins cannot edit/remove owners or admins. The sole owner cannot be demoted or removed; ownership transfers only through a dedicated operation that atomically promotes an existing active member and demotes the former owner to admin. Owner creation is never accepted from client payloads. Suspended organizations deny all tenant operations except owner-only reactivation. Users can still see their own suspended membership in the account organization selector.

Every tenant service rechecks active user, organization and current membership; staff/superuser status grants no tenant API bypass. Inaccessible tenants and cross-tenant nested objects return 404; authenticated role failures and anonymous session denials return 403. Writes lock the organization before checking membership and mutating, serializing transfers/revocations/role changes. Nested lookups always include the authorized organization. Strict serializers reject unknown/read-only ownership fields. There are no bulk endpoints, hard deletion APIs or product resources. Audit listing requires owner/admin. Application isolation is mandatory; PostgreSQL RLS is not implemented.

Audit success records commit atomically with business changes. Failed authentication and selected authorization failures are separate failure events, without submitted credentials, identifiers, headers, IPs or usernames. Metadata permits only role transitions. Audit records expose no modification API and have read-only admin integration; ORM instance/queryset update/delete guards are an additional convention, not a database-level tamper guarantee. Organization deletion is blocked by audit references; actor deletion nulls the actor reference. Memberships protect user deletion. Operators/DB owners remain trusted and need separately governed access. Provisional audit retention is 365 days pending legal/customer review; implement a reviewed privileged archival/purge process before launch. No automatic purge or external immutable sink is claimed.

DRF throttles provide per-process best-effort abuse limits, not distributed brute-force protection. Production requires shared ingress rate limits, request body limits, TLS, proxy-header sanitation and operational monitoring. Local development is loopback HTTP only.

Acceptance review: new-registration character validation is not imposed on existing Django usernames at login. Organization selection pins the newly created server-returned membership and merges later pages by membership ID, taking refreshed server roles. These client values remain presentation state; every API request is still authorized independently.

A repeated live proxy sequence exposed Node HTTP socket reuse failures (`ECONNRESET`) before authenticated CSRF retrieval. An isolated diagnostic with a fresh-socket agent passed 40 consecutive authenticated reads. A Node preload, configured in both npm runtime scripts and the production Docker entrypoint, now sets the process's default HTTP agent before Next.js imports its proxy. The later instrumentation hook did not reliably cover the routing process and was removed. This is a process-wide HTTP transport policy, adds a connection per request, and does not retry mutations or alter CSRF/TLS validation. Revisit connection pooling only after an upstream fix and realistic throughput tests. Reference: [Node HTTP agents](https://nodejs.org/api/http.html#httpglobalagent).
